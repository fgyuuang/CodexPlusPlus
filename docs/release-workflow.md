# 后台检查、编译和交付

## 成功产物重新交付（2026-11-12）

已有成功构建、只需再次复制到安装目录时，可使用 `Redeploy`。它同步执行短交付任务，不查找或调用 Cargo/Node，不重新运行测试或构建；会返回新的任务编号和最终状态。它交付指定构建的版本，不包含当前源码后续修改。源码变化需要继续使用 `Start`。

```powershell
# 指定完整成功构建，默认只交付到 bin
pwsh -NoProfile -File .\scripts\release.ps1 -Action Redeploy -Job '20261111-220934-d6298f83'

# 同时更新已授权的现有安装目录
pwsh -NoProfile -File .\scripts\release.ps1 -Action Redeploy -Job '20261111-220934-d6298f83' -DeployTo 'D:\pro\Codex++'
```

从本功能启用后的完整发布开始，新产物保留在任务的 `artifacts/` 中；交付不再消耗这份封存。重新交付会验证原任务来自本仓库、完整步骤均成功、平台、EXE/DLL 文件集及哈希，再将文件封存到新任务后执行既有备份和替换流程。独占锁、编译进程检测、失败恢复和最终哈希仍有效。不得将 `target/release` 中后来生成的文件冒充原版本。

旧任务没有封存与平台记录时，仅允许仓库 `bin` 的全部产物与原成功清单完全一致，并通过 EXE 的 PE 架构核对，才迁入新任务封存；任意文件缺失或不匹配均拒绝，不从其他目录猜测补齐。仅有旧文件备份不能证明它们是该次发布的新产物。

新任务的 `request.json` 记录来源任务及原清单哈希，`source-status.json` / `source-request.json` 保留来源证据，`status.json` 记录本次交付。原构建记录不会被覆盖。不自动重启应用、不改变账号、配置或历史；用户仍需自行安排退出、重开和实际功能验收。重新交付不会完成配置或数据库降级迁移。

也可将成功的重新交付任务编号传给 `-Job`，复用其封存。工具会追溯并验证原始完整构建证据，`sourceJob` 始终记录原构建，`copiedFromJob` 记录本次封存来源；原始记录被改动则拒绝。旧版本迁入后应保留新任务编号，这样以后 bin 已升级也能复用封存。

隔离测试使用假构建工具，覆盖完整封存、源码与 target 已变化、零构建调用、旧任务迁入、损坏/缺失文件拒绝、独占锁及部分替换失败恢复。测试命令仍为 `pwsh -NoProfile -File .\scripts\release.tests.ps1`。只修改此发布工具无需重编产品 Release。

日常小改动先参照[快速开发与缓存管理](development-workflow.md)做热更新或定向验证，收敛后再启动一次完整发布。定向检查不等于交付成功；纯文档修改无需重编产品。开发缓存应复用，只有空间不足或阶段性交付后才清理。

## 测试与编译的固定交接

一个发布任务连续完成以下阶段，全部测试通过后自动向后执行，无需再次确认：

| 阶段 | 状态中的步骤 | 完成条件及后续动作 |
| --- | --- | --- |
| 检查与测试 | renderer-check、rust-fmt、rust-check、test-codex-plus-core/data/manager、typescript、frontend-tests | 所有步骤退出码为 0，构建输入未变化，自动进入构建 |
| 前端构建 | vite | 生成并验证最新 dist，自动进入正式编译 |
| 正式编译 | release | 执行 cargo build --workspace --release，不再运行测试 |
| 核对与交付 | 后续核对与复制，最终 complete | 编译进程结束、源码与产物哈希通过、备份及目标文件核对成功，state 才变为 succeeded |

`cargo test` 需要先编译测试可执行程序，再运行其中的测试；这部分属于第一阶段，不能和最终 Release 编译混称。进度报告应明确当前阶段、已通过的步骤、是否产生并交付正式程序。

完整检查及测试由后台任务统一执行一次。开发时按改动做定向回归，不在启动后台前重复跑同一套完整测试。任务进入 vite / release 后，不插入额外测试、清缓存或修改冻结输入；正常任务继续执行至交付，不因耗时重启或并行另起构建。

每次发布都由 Agent 跟踪至最终交付核对，不需要用户反复追加“追踪直到完成”。核对已完成步骤的退出码，确认原任务自动转入后续阶段；检查及测试期间每 30–60 秒读取状态和当前日志，及时发现错误。后台脚本负责执行，阶段之间没有人工放行门槛。

状态仍为 running 时也要检查当前日志的编译错误、FAILED、异常退出和栈溢出。`--no-fail-fast` 会在某个测试程序失败后继续运行其他程序，不能仅因工作进程仍活着而报告“没有错误”。发现失败立即记录并告知，待原任务及相关进程退出后再应用修复，避免改动冻结输入或遗留孤立测试进程。

进入耗时的 Release 优化、链接阶段后，保留当前任务并等待，每次 45–60 秒后检查状态；单次阻塞不超过 60 秒，避免紧密轮询。阶段变化、失败和交付结果及时告知，正常编译只作简短进度说明。若疑似停滞，对比两次进程 PID 与启动时间、CPU/IO 增量、日志更新时间和退出码；日志暂时不更新、任务超过 30 分钟均不足以证明卡死。不能为缩短等待降低 Release 优化或清空缓存。

失败时立即记录失败步骤、退出码和日志，告知当前尚未完成交付；确认旧编译进程退出后修复对应问题，按新输入启动一个新任务并继续跟踪，不能结束在“已重新提交”。跨任务复用测试结论必须证明源码、依赖、工具链和构建配置一致；当前脚本不提供跳过测试的发布入口。只修改未纳入构建快照的说明文档，不使正常任务失效，也不要求重编产品。

Agent 完成改动、必要的针对性验证和分片组装后，启动一次后台任务并继续等待、检查及纠错，直到 `state=succeeded`，且步骤退出码、产物、备份、目标文件哈希和进程路径核对通过，再结束本轮。提交后台任务、测试通过、进入 Release 均不是交付完成。用户明确停止或存在必须由用户处理的阻碍时，交代任务编号、状态、错误和恢复条件，不能无说明搁置任务。应用重启及真实界面验收仍由用户安排，不自动重启、提交或推送。

从仓库根目录启动：

```powershell
# 默认交付到仓库 bin/；前端改动传入能标识本次修改的文本/标记
pwsh -NoProfile -File .\scripts\release.ps1 -Action Start -ExpectedUiText '本次功能的独特文本'

# 已获授权更新现有安装目录时，显式指定目标
pwsh -NoProfile -File .\scripts\release.ps1 -Action Start -ExpectedUiText '本次功能的独特文本' -DeployTo 'D:\pro\Codex++'
```

启动命令返回任务编号、PID 和证据目录，随后独立的隐藏 PowerShell 进程继续工作。任务不依赖本轮聊天继续执行；不使用 `Start-Job`，不创建可见窗口。纯后端修改可省略 `-ExpectedUiText`，默认仍刷新 Vite 以避免嵌入旧资源。

`-ExpectedUiText` 应选择该功能实际使用的稳定 DOM id/class 或界面文本，不能选会被压缩改名的函数名。v2.4.0 原生登录控件可用 `native-auth-account`；`nativeAuthSelection` 是源码函数名，Vite 成功也不会保留它。启动前检查标记是否适合产物格式；旧 dist 中存在标记只用于排除错误参数，不能代替本轮 Vite 时间戳、文本和哈希验证。当前脚本没有续跑或跳过测试入口，标记选错会使完整测试后仍被门禁拦住，应在启动前确认。

跟踪期间在有界等待后查询同一任务；以下命令只读取状态，不重新启动编译：

```powershell
pwsh -NoProfile -File .\scripts\release.ps1 -Action Status
pwsh -NoProfile -File .\scripts\release.ps1 -Action Status -Job '返回的任务编号'
```

状态含义：`queued` 等待启动，`running` 正在执行，`succeeded` 完成检查及交付，`failed` 某项失败，`interrupted` 工作进程意外退出。状态中包含当前阶段、日志、错误、产物 SHA-256、备份和交付路径。检查 PID 时同时校验进程启动时间，避免 PID 复用造成误判。

脚本顺序执行：

1. 获取工作区独占锁并检查是否已有 Cargo/Rustc/Link/Tauri 编译进程，禁止重复任务。
2. 校验交接时的源码文件列表与 SHA-256，包括新建、删除文件；构建输入含 Rust、Manager、assets、scripts、内嵌图片及 Cargo 配置。
3. renderer 组装一致性、Rust fmt、`cargo check --workspace --all-targets`、core/data/Manager 测试、TypeScript 和前端测试。前置 check 同时覆盖独立集成测试和 Manager 测试的编译类型，避免普通 workspace check 通过却在后续测试目标发现遗漏字段。Rust 使用当前 Cargo、默认 `-j 2`，共享测试单线程。
4. 执行项目已有 Vite CLI（与 `npm run vite:build` 相同），检查 dist 更新时间与指定文本，再构建 Rust Release。不会调用会打安装包的 `npm run build`。
5. 等待编译进程结束，重新核对源码、dist、Manager 时间戳、三个 EXE 及必要运行时 DLL 的 SHA-256。
6. 为全部目标先备份并核对，再交付到 bin/ 和显式指定的运行目录，逐文件核对最终哈希。失败会停止后续步骤；替换过程中失败时尝试恢复已替换的旧文件。
7. 落盘最终状态与摘要，列出当时运行的 Manager/启动器及实际路径，不结束或重启任何应用。

源码漂移、校验失败、UI 标记缺失、旧 Manager 产物或非零命令退出都会阻止交付。脚本不自动重编译或重试整轮发布；修复对应问题后再启动新任务。已在编译时继续修改源码，原任务会失败并保留日志，不能把它当作新改动的构建。

多个对话共享工作区时，写源码、组装分片和编译前先查询发布状态；正常任务冻结期间，其他工作在隔离目录继续。监督者确认输入已经漂移时，应记录变化文件和已核实的发布进程树，仅停止这一轮已失效的 worker 及其测试/编译子进程，保留日志、备份和并发修改，不结束用户应用。审查并发改动后按新输入重新发布；这与因正常编译耗时而重启任务不同。

默认需要已安装的 Node 24+（运行 TS 测试）、Cargo、rg 和项目 node_modules；优先使用现有 Node，也会尝试当前用户已有的 Codex Node 运行时。可用 `-NodePath`、`-CargoPath` 明确已有工具路径，`-Jobs` 设置并行度。不安装依赖、不切换 Rust 工具链。

证据保存在 `output/release-jobs/<任务编号>/`：

- `request.json`：交接参数、冻结输入清单。
- `status.json`、`summary.md`：状态与交付结论；`frontend.json`：本次 dist 清单。
- 各步骤 `.log`，以及进程启动阶段的 `worker.out.log`、`worker.err.log`。
- `backup-bin/`：仓库 bin 旧文件；运行目录旧文件在其 `backups/release-<任务编号>/`。

不自动删除日志、备份和未完成的中间文件。首次交付到原本没有文件的 bin 时，若交付中途失败，已新建的文件保留供检查；状态仍为失败。意外终止时也不得视为交付完成，应根据清单核对恢复。脚本不读取或修改真实 config/auth、账号设置及聊天数据库，不提交、不推送。应用重启及界面验收仍由用户安排。

Windows 的离线语音使用 sherpa-onnx 1.13.8 共享库，保留完整功能，避免其预编译静态 STL 要求比本机 MSVC 14.37 更新的开发库。三个 EXE 名称和路径保持不变，但交付时必须连带 `sherpa-onnx-c-api.dll`、`onnxruntime.dll` 及同一原生库包中的运行时 DLL，不能只复制 EXE。库文件由 Cargo 的 sherpa-onnx-sys 构建步骤复制到 `target/release/`；发布脚本只接受与锁定版本的 `target/sherpa-onnx-prebuilt/sherpa-onnx-v<版本>-win-<架构>-shared-MT-Release-lib/lib/`（或显式 `SHERPA_ONNX_LIB_DIR`）逐项哈希匹配的 DLL，缺失或不匹配就停止交付。它不会扫描或分发系统 CRT/Windows DLL，也不删除目标目录旧文件。所有运行库与 EXE 共用备份、原子替换、失败恢复和最终哈希检查；`status.json` 的 `runtimeDependencies` 保存原生包来源，`artifacts` 和 `delivery` 列出完整文件集。

只修改脚本/文档时无需重跑产品 Release。验证脚本流程用隔离假工具：

```powershell
pwsh -NoProfile -File .\scripts\release.tests.ps1
```

该检查验证后台返回、空格路径、并发锁、成功交付及备份哈希、默认只更新 bin、失败停止、源码新增/dist 变化检测、UI 缺失/旧 Manager 拦截和遗留状态识别；不会调用真实 Cargo/Node 构建，也不会修改真实安装目录。测试目录保留在 output 下。
