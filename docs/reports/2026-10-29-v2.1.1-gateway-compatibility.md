## 故障及修复

1. 网关写入托管配置时只留下当前 transport provider，旧对话仍保存 `codex_plus_official_schedule`，恢复时原生 Codex 因 provider 不存在拒载。配置写入现保留已经确认的本地同名 routes 定义；不保留同前缀第三方地址或用户其他配置，不改当前根 provider。旧账号路由的解析与菜单生效状态分开：网关可隐藏旧菜单，旧聊天仍按原账号和模型验证。没有改历史 provider、聊天 ID、SQLite 或 rollout。
2. 本地账号引用没有独立 token 快照，普通成员目录生成器不能取得官方模型显示元数据，选择器回退到 `local-official-<hash>/模型`。网关目录改读被引用账号自己的缓存；无缓存时仅提供可读名称，不杜撰 reasoning、上下文或其他能力。路由 ID 原样保留；审批内部模型遵循上游的目录隐藏规则。
3. 请求提示曾直接显示 `codex_plus_official_schedule:gpt-6.1-sol`。现按真实请求来源显示模型与账号名称；未选定则显示「正在选择账号」。受保护请求在验证所选账号凭据后发布来源，网关按候选请求发布来源；作用域绑定请求 ID，调度换号更新同一请求，其他请求不受影响。接口只给出脱敏名称与模型，不输出凭据；不改变出站模型、账号或回退策略。

用户报错后的只读检查发现网关已经关闭，旧调度定义恢复。当前真实 config.toml 的 TOML 解析及原生 `app-server --strict-config --stdio` 均通过，未为排查重写真实配置或登录。本轮修复防止再次接入网关后重现；新版运行验收仍需单独进行。
