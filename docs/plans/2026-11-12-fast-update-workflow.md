# 快速更新流程设计（2026-11-12）

状态：设计后已开始实施第一阶段“成功产物重新交付”，入口及当前约束见 [发布说明](../release-workflow.md#成功产物重新交付2026-11-12)。本文后续阶段仍是设计，不替代 AGENTS.md 的正式发布门禁，也不表示已升级上游或验证兼容。

## 结论与目标

长期采用“官方发布包 + 独立扩展 + 少量必要兼容”，让常规上游更新不依赖本机 Rust 编译。过渡期保留源码发布，先实现已验证产物重新交付，再实现同输入阶段恢复；不同源码的测试结果不直接复用。优化成功以本机测量为准，不承诺每次源码发布能缩短到几分钟。

## 审计发现与边界

- P2：scripts/release.ps1 当前只有 Start/Status/Worker；失败后的新任务仍完整执行，不能安全复用已有成功阶段。
- P2：每次固定运行 Vite，再以 Manager 时间戳晚于 dist 为交付条件；即便前端内容没变也没有按内容证明复用的入口。不能只跳过 Vite 或删除时间戳检查。
- P2：所有 Rust 测试统一单线程。共享路径用例需要保留该限制；纯单元用例可作为后续隔离审计对象，不能直接全局提高测试线程数。
- P2：当前 MERGE_HEAD 仍为 v2.4.0，HEAD 是较早的 v2.0.0 整合提交；跨轮工作尚未收敛为清晰提交，增加下次合并审查成本。实际新版启动验收后再整理提交，不能仅凭构建成功擅自提交。
- 暂不移除：加密账号引用、旧 provider 恢复、官方图片目标隔离，以及插件依赖的本地宿主接口。docs/local-features.md 记录 CLIProxyAPI/NewAPI 虽已有插件界面，服务生命周期和 DPAPI 仍由宿主提供；界面插件化不代表已脱离 fork。
- 本次未发现必须立即停止现有发布流程的 P0/P1。范围决策：发布模块为 Refactor Backlog / Staged Refactor；本轮授权为设计，运行逻辑仍采用现有流程。

## 三种更新路径

| 变化类型 | 推荐路径 | 核对与交付条件 |
| --- | --- | --- |
| 独立用户扩展、样式、配置 | 扩展包更新或配置迁移，不编译 Rust | 依赖宿主 API 可用，包版本/哈希、备份、加载与功能验收 |
| 上游版本，全部本地必需能力已有兼容实现 | 官方 Windows 成品包更新 | 发行包校验、账号/历史/扩展兼容门禁、完整文件集和回滚 |
| Rust 核心或宿主接口仍需本地补丁 | 源码发布 | 定向验证收敛后一次全量门禁，沿用现有 Release 参数 |

Manager 内嵌前端变化仍属于宿主发布；不能把 dist 文件随意复制到安装目录就视为更新。配置变更也必须验证，涉及 config.toml 时先按规定备份。独立扩展仅承担开放 API 能实现的行为，不通过拓展权限绕过认证或注入任意宿主路由。

## 第一阶段：已验证产物重新交付（优先实现）

最小改动落在 scripts/release.ps1 与 scripts/release.tests.ps1，不重写整个发布系统。第一阶段入口为 `-Action Redeploy -Job <成功构建编号>`，其余阶段仍待实现。

1. 只接受 state=succeeded 且全部步骤退出码为 0 的任务；校验任务版本、目标平台、受信任仓库来源和原始发布清单。
2. 复制使用该成功任务封存的产物；不从可能已被覆盖的 target/release 临时取文件。逐个验证三个 EXE、四个 DLL 及来源记录。
3. 创建新的交付任务，关联原构建任务；验证目标目录、运行进程和独占锁，备份、替换、哈希检查及失败回滚保持现有规则。
4. 当前源码可以比封存产物更新，但必须明确交付的是旧任务对应的源码快照，不能宣称包含当前修改。
5. 验收：隔离假工具验证重新交付零次调用 Cargo/Node、损坏/缺失/替换产物被拒绝、目标备份与恢复、DLL 完整性、并发锁、旧任务证据不改写。

收益：仅重新替换同一已验证版本时无需再等待约 69 分钟；这是减少重复工作的首个低风险切口。不能用于把新源码冒充已构建版本。

## 第二阶段：同输入阶段恢复

在第一阶段稳定后增加显式恢复入口；不提供无条件 SkipTests。恢复任务保存新的状态与引用，不篡改原失败任务。

- 每个成功步骤保存输入清单及哈希、精确命令、工作目录、工具版本与二进制身份、平台/架构、依赖锁、相关环境白名单与有效编译配置、输出哈希、结束状态。
- 第一版采取保守的整套构建输入一致要求，覆盖新增/删除文件、测试、脚本和生成资源；不只比较 Git HEAD、版本号或文件时间。捕获必要环境时不记录凭据。
- 源码、工具链、依赖、构建配置任一变化即失效并重跑；缺证据、未知环境、异常退出也重跑。需要外部服务的检查不得无期限缓存。
- 编译失败但前置完整测试成功，且所有测试输入仍一致，可以复用该完整测试证据；源代码修复后必须重跑。仅交付失败且完整产物有效，可以重试交付。
- Vite 内容复用须同时证明源输入和 dist 内容一致，Manager 清单记录实际嵌入的 dist 摘要。届时以构建关联证据取代单纯时间戳判断；证据不足走现行全流程。
- 不并行执行测试和正式 Release；完整测试证据必须先建立。首次启用需要同步修改现行发布规范，不能先偷偷跳步骤。
- 验收：输入新增/删除、工具链变化、测试脚本变化、dist 篡改、缺产物、失败阶段均不误命中；同输入恢复只执行失效阶段，最终交付仍逐项验哈希。

不同模块的细粒度缓存放到后续：必须先建立 Rust features、构建脚本、内嵌资源、前端依赖的实际影响关系，未知变更默认全量。不得凭“只改了一行 UI”推断后端必然不受影响。

## 第三阶段：官方成品包成为默认更新通道

先在隔离目录完成兼容验证，再切换实际安装。不能同时让两个版本共享可写账号库与历史数据库；若使用测试配置副本，应使用受保护目录并禁止并发刷新同一账号凭据，不能将真实凭据放进普通构建产物或日志。

| 本地能力 | 迁移方向 | 切换成品包前的证据 |
| --- | --- | --- |
| 官方账号库引用及多账号 | 上游原生账号/网关，必要时一次性迁移 | 已有登录继续有效、唯一刷新所有者、额度查询、自动组和模型精确来源 |
| 旧聊天 provider | 上游恢复能力或有限迁移 | 原会话/分支可继续，单会话备份可恢复，不批量改写正文 |
| CLIProxyAPI/NewAPI 管理 | 独立扩展及外部服务 | 启停、凭据保护、配置和故障恢复；外部服务数据保留 |
| WorkBuddy/Claudian | 上游 Agent 接入 + 独立协作扩展 | 模型接入与 CLI 执行分别验证，不把连通性等同任务成功 |
| UI、菜单及显示增强 | 公开拓展 API | 不依赖本地私有宿主补丁，升级后加载和卸载正确 |

官方包下载先校验平台、正式版本和上游 SHA256SUMS，再按可用的签名机制验证来源；同站点哈希不等同独立签名。安装完整发布包，不能把本地旧 DLL 与官方新 EXE 随意混搭。

回滚包含“程序 + 版本相关配置/数据快照”的一致恢复；新版本若发生 schema 迁移，只有旧 EXE 备份不足以回滚。升级期间产生的新对话需要保留或单独导出，不能盲目覆盖回旧数据库。

通过上述全部必需能力后，常规补丁更新只下载和部署成品包，实际时间取决于网络、迁移与验收；尚无本机提速实测。若任何必需能力未覆盖，继续最小补丁源码发布，不静默降级功能。

## 开发、缓存与发布管理

- 开发复用现有 Vite 热更新、cargo check 和定向测试，多个相关修改收敛后发布一次；不把 debug 产物复制为正式版本。
- 保留一个主开发 target 和受控的发布缓存；不每次交付后清空 debug。空间紧张时先预览、按授权回收过期产物，保留正在使用的依赖缓存、证据和必要回滚版本。
- 保持工具链、features、目标平台与编译配置稳定，减少无意缓存失效。CPU jobs 调整需结合内存峰值与实测，不能假定加倍并行会使 fat LTO 加倍提速。
- 可以后续使用缓存构建机代替本机等待，但必须产出相同测试/快照/哈希证据，不上传账号数据；只是迁移计算位置，不保证总耗时下降。
- 发布仍为单个独占任务，失败及时发现，正常优化期间每 45–60 秒检查，Agent 跟踪至交付核对完成。进度显示基于历史范围而非虚构百分比。

## 实施顺序与验收标准

1. 当前：保留已成功交付版本，完成用户运行验收后收敛已有合并提交；建立这份耗时基线。
2. 首个代码阶段：只实现成功产物重新交付及隔离脚本测试，目标 2 个代码/测试文件、每阶段约 200 行以内；超过预算另拆阶段。不涉及产品源码时不重编产品。
3. 第二个代码阶段：逐步加入完整证据记录和同输入恢复；先用假工具验证失效矩阵，再对下一次必要发布测量。保留现有全流程入口作回退。
4. 对 v2.6.6 做正式差异与兼容审计，优先消除已被上游覆盖的补丁；本次尚未授权/执行新的合并，不修改当前 v2.4.0 整合目标。
5. 长期迁移验收通过后，官方成品包为默认；需要本地 Rust 补丁才进入源码发布。

验收指标：重复交付调用 Cargo/Node 次数为 0；恢复不能使用过期测试证据；任何交付均有完整文件哈希及回滚；实际记录冷/热缓存时长与磁盘增量。证据缺失则走全流程，不以“优化成功”掩盖未执行的验证。

本轮仅审计现有日志、脚本、配置和维护清单，未运行构建或迁移实验。流程提速、官方包兼容和细粒度测试选择均属于待实现/待验证能力。
