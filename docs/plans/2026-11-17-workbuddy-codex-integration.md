# WorkBuddy 与 Codex/Codex++ 完整接入评估及实施方案

日期：2026-11-17。状态：方案评估，尚未实施。基线：本机 WorkBuddy Manager v2.6.3、Codex++ v2.6.10 工作区、已安装 WorkBuddy Manager 用户拓展 0.8.1。

## 1. 目标与推荐结论

用户在 Codex 中通过现有模型选择器使用 WorkBuddy 提供的模型并完成真实开发任务；账号添加、导入、分组、签到、刷新、权重调整、积分查询和调用故障处理均在 Codex++ 中完成。日常管理不依赖切换外部浏览器或手动复制模型 Key。

采用“普通供应商接入 + Codex++ 内的 WorkBuddy 管理拓展”，两者共享后端连接身份。供应商界面以用户 2026-11-17 提供的现有卡片截图为基准：

- Codex 对话只负责通过现有模型选择器和网关使用模型；本方案不新增 Codex 管理入口、状态侧栏或页面注入。
- Codex++ 网关：WorkBuddy 作为普通供应商，沿用名称/协议/地址/状态、模型、生图模型、Key、更多设置、测试和删除的既有布局与交互。供应商卡片不增加 WorkBuddy 专属摘要、管理按钮组或账号表。
- WorkBuddy 管理页：统一承载账号、积分、模型、用量和服务操作，复用原 Manager API 与成熟业务组件逻辑。

保留网关查看积分的目标，但通过面向各供应商的通用额度能力接入，明确积分单位和作用域；当前通用接口无法承载的内容先在管理页完整展示，记录为待补能力，不能用专属供应商卡片替代。

模型请求继续经过 Codex++ 网关和 Manager 的模型 API。Manager 与 workbuddy2api 继续持有并管理原有账号池；界面层不复制其调度器。完整网页嵌入作为独立可行性验证，不作为其他模块开工的前提，也不作为“接入完成”的唯一验收依据。

| 项目 | 已核实 | 对方案的影响 |
| --- | --- | --- |
| 模型调用 | 现有适配读取 `/v1/models`，创建/更新普通供应商，提供终止事件检查 | 继续复用已有网关与供应商，不增加第三个模型代理 |
| 当前拓展 | `local-services-independent` 0.8.1 已启用、loaded；管理页与后台已存在 | 后续通过拓展工具更新同一个包 |
| 重复连接候选 | `workbuddy-provider-connector` 0.1.0 当前停用 | 先审查并沿用活动供应商身份，不自动同时启用两条连接 |
| 多供应商连接 | 宿主按 `source=workbuddy` 查找第一个供应商，接入参数没有连接/分组 ID | 多账号池分别接入前必须解决身份与写入范围 |

| 原生统计 | Codex++ 已按日期、Agent、供应商、模型累计用量 | 本地调用统计直接复用；不导入 Manager 全量用量再累加 |
| 网关额度显示 | 当前拓展供应商声明没有积分/账号摘要回调；Manager 页没有供应商行插槽 | 后续对接通用额度契约；不为 WorkBuddy 增加专属供应商行或摘要卡，不能声称纯改拓展已完成 |
| 完整网页 | Manager 禁止嵌入；Codex++ 管理页有独立 CSP 与无同源的 iframe 沙箱 | 改 Manager 两处响应头后仍要验证宿主与 Cookie |
| 真实运行 | 本轮只读健康检查曾通过，已有进程可见 | 不代表模型、扫码或管理登录已在本轮验收 |

## 3. 架构与数据归属

```text
Codex 模型选择与任务
  -> Codex++ 现有网关（供应商、路由、本地请求统计）
    -> WorkBuddy Manager /v1（Key 鉴权、额度、模型映射、协议适配）
      -> workbuddy2api（账号选择、刷新、并发、冷却）
        -> WorkBuddy 上游

Codex++ 内的 WorkBuddy 管理页 / 网关通用额度能力（待对接）
  -> 同一个 WorkBuddy 拓展后台适配
    -> Manager /api、/v1/usage 与已有本机控制器
```

| 数据 | 唯一主要来源 | 展示约定 |
| --- | --- | --- |
| Codex++ 发出的模型请求 | Codex++ UsageStore / 请求日志 | 可按 Codex、供应商、模型过滤 |
| Manager 接收的全部请求 | Manager 用量和请求日志 | 标记“Manager 全部调用”；包含其他客户端时如实显示 |
| 上游积分余额、到期批次 | Manager 账号积分接口/快照 | 标注账号池、来源、观测时间和覆盖率 |
| 模型 Key 已用与上限 | Manager `/v1/usage` | 无限制显示“不限额”；不限额不代表账号池无限积分 |
| 账号运行状态与权重 | Manager/workbuddy2api 的实际接口 | 操作完成后回读；文件存在不等于已加入可用池 |
| 模型上下文/思考/图像能力 | Manager 目录、供应商目录及能力验证 | 未提供的字段保留未知；不按模型名称猜测 |

工作区现有 ChatGPT 配额窗口与重置时间功能继续保留。WorkBuddy 展示积分余额及到期批次，不复用“5 小时剩余百分比”语义。

## 4. 稳定连接身份与多账号池

建立可迁移的连接记录，逻辑上包括：`connectionId`、Manager 服务实例、`realm`、`upstreamId`、`providerId`、Manager 模型 Key 的非敏感记录 ID、账号池引用及受管进程引用。字段名称在实施时按已有契约收敛，不直接创建第二套供应商库。

- 第一次识别既有 WorkBuddy 供应商并建立绑定；默认保留 providerId、模型别名、路由组和历史。
- 一个连接绑定一个明确上游账号池；一个 Manager 可有多个连接。
- 同池多个 Key/连接共享积分池标识，汇总池余额只计一次；Key 额度分别显示。
- 账号权重决定池内账号选择；Codex++ 供应商/模型组权重决定池之间的请求路由。界面明确区分两种权重。
- 默认先支持已有默认池；多池需要明确上游接入点可用、账号目录可管理。不能承诺新建分组时自动生成新的网关进程。
- 修改或停用一个连接只作用于其绑定对象；不得用服务名模糊命中另一个连接。

## 5. Codex 使用边界与 Codex++ 管理界面

### 5.1 Codex 对话

保留现有模型选择器与供应商/模型身份，通过 Codex++ 网关调用 WorkBuddy。无需为本方案修改 Codex 界面或新增页面注入。

供应商/模型、Key 和测试交互沿用 Codex++ 网关现有界面；账号池、积分、管理操作结果及刷新时间主要放在 WorkBuddy 管理页。网关中的积分回显通过通用额度机制承载。只有能从可靠请求身份判定连接时才标记对应关系，不猜测当前对话来源。

普通使用不要求模型调用任何管理工具。签到、积分刷新等来自 Codex++ 内的用户操作；运行中的开发任务不会因打开管理页或查看状态而被重启。页面关闭/隐藏时停止对应轮询。

### 5.2 Codex++ 网关

严格复用现有普通供应商卡片。用户截图中的层次作为交互基准，内容按真实配置动态填写：

```text
WorkBuddy                              新模型提示 / 可用状态 / 启用 / 展开
Responses · 服务地址 · 模型数量
  模型         模型标签 / 显示全部
  生图模型     模型标签（按现有通用分类规则显示）
  Key          脱敏 Key / 现有测试、编辑、删除、添加 Key 操作
  更多设置     价格、上下文窗口、思考等级、代理、限速
  测试                                                        删除
```

具体约束：

- 模型拉取、新模型提示、全部模型展开、Key 管理、连通测试、开关、排序和删除均使用已有供应商流程。不因名称或 source 等于 WorkBuddy 而更换组件。
- 思考等级和上下文窗口继续使用“更多设置”中的通用入口，补齐元数据读取、映射和保存；不再增加 WorkBuddy 专属档位面板，也不为每个思考档位复制供应商或模型条目。
- WorkBuddy 模型 Key 继续作为普通供应商 Key 保存；账号 Token、管理登录与模型 Key 各自保留原有职责，不将 WorkBuddy 的每个上游账号转换成 Codex++ 供应商 Key。
- 扫码、导入、分组、账号状态/有效期、签到、刷新、账号权重与积分批次在 WorkBuddy 管理拓展中完成。管理后更新同一普通供应商及其绑定，保留 providerId、路由配置和历史。
- Codex++ 本地模型用量沿用通用统计入口；Manager 的全量用量及账号明细在管理页展示，不在供应商卡片另铺一套统计。
- 网关显示积分时使用可复用于其他供应商的额度区域/入口与数据契约，明确单位、Key/账号池作用域、观测时间和未知状态；不加入 WorkBuddy 专属账号数量、签到或快捷按钮组。该通用能力尚未对接完成时，卡片保持截图中的形态，积分仍可在管理页查询。
- 积分查询读取共享缓存，不自动逐一刷新所有账号，不阻塞供应商列表或模型请求。同一池的多个 Key 不重复累计池余额。

### 5.3 WorkBuddy 管理页

建议五个业务页签：概览、账号、积分、模型与连接、用量与任务。服务地址和进程控制进入设置面板，避免占据首屏。

- 概览：服务可达性、上游池状态、管理登录、供应商绑定、最近验证、需要处理的问题。主操作只保留当前最需要的下一步。
- 账号：搜索、分组与状态筛选、可排序表格；显示昵称、状态、余额、授权到期、积分到期、签到、权重；支持扫码添加、导入和常用批量操作。
- 积分：已登记余额、最近查询时间、到期批次、账号明细、收入记录和模型消耗。区分“登记收入近似值”与“上游返回的调用消耗”。
- 模型与连接：模型选择、能力详情、默认模型、真实请求验证、供应商绑定及 Key 管理。
- 用量与任务：区分“本机 Codex++”和“Manager 全部调用”；模型筛选、请求失败详情、定时任务状态及执行记录。

使用 Codex++ 字体、主题、按钮和间距；宽屏用紧凑表格，窄屏将次要字段折入详情。保留搜索、分页、排序、滚动位置；弹窗支持键盘、明确标签和可见焦点，状态不只依赖颜色。

## 6. 关键交互流程

### 6.1 首次连接与已有配置恢复

1. 检查既有服务与供应商绑定；展示发现的状态，不重复创建。
2. 服务未启动时提供单个“启动服务”，已存在的受管操作显示进度与操作编号。
3. 管理功能需要登录时内嵌登录；模型调用状态可以独立读取。
4. 没有可用账号时进入扫码添加/导入；有账号时直接选择已有池。
5. 优先使用已保存调用 Key；确需新 Key 时在“连接到 Codex”流程中明确选择创建专用 Key，并绑定正确池。
6. 读取当前 Key 可见模型；选择模型并执行真实流式验证，再更新原生供应商及 Agent 配置。
7. 分开确认：供应商已保存、Codex 配置已刷新、模型可选、真实 Codex 请求已成功。某一步失败时停留在该步骤并保留前面结果。

Key 明文只在创建时返回一次，Manager 数据库仅保存哈希。新 Key 返回后应先在后端安全保存，再向 UI 返回非敏感结果。响应丢失或创建状态未知时先查询原操作，不能自动再创建一把 Key。

### 6.2 扫码添加

选择明确的目标池与版本，调用原 `/api/auth/start` 与 `/api/auth/poll`。流程区分二维码准备、等待扫码、等待授权、写入账号、上游重载、已加入池、失败/过期。扫码被确认不能直接算账号可用了。

沿用 Manager 后台轮询/落盘机制，前端恢复焦点时补查状态。避免拓展和 Manager 各自重复启动同一个扫码任务；重新生成二维码应有明确的旧任务处理。

### 6.3 导入与账号管理

导入先校验格式、目标池和重复项，展示新增/更新/冲突数量，再调用原上传 API；返回逐项结果。失败可只重试失败项。文件内容通过专用接口传给 Manager，不写进普通配置、日志或对话。

签到、刷新、权重、启停、备注、移动分组等使用既有 API，完成后回读真实状态。批量操作显示已完成/失败/未执行数量；一个账号失败不清空整个页面。

高频普通操作直接执行；删除账号、覆盖导入、停服务等会影响现有状态的动作显示对象和结果提示。后台结果未知时提供查询入口，不自动重复提交。

### 6.4 使用中失败与恢复

对服务离线、Key 失效/限额、池无可用账号、账号过期、模型不允许、限流和断流给出不同处理入口。对模型请求保持原始错误和终态；不把 HTTP 200 或 CLI 退出码作为成功。

管理登录失效只让管理操作重新登录，不自动关闭仍可用的模型连接。查看余额失败不自动把供应商下线。连接故障不自动重放可能已执行工具的整轮任务。

## 7. 完整页面嵌入的评估

本地 Manager 源码可改，`X-Frame-Options` 与 `frame-ancestors` 不是不可修改的限制。需要验证的还有宿主 CSP、sandbox 的不透明来源、Cookie 登录、Next.js 路由/静态资源、扫码/弹窗/导出、主题和窗口尺寸。

先做隔离验证：使用备份源码/隔离实例及独立浏览器上下文，测试准确的目标宿主；不先重启真实服务，不先放宽所有拓展的沙箱。

通过标准：页面完整加载；登录/刷新/退出稳定；账号页导航不丢状态；扫码授权回流可用；窄窗口可操作；只有预期页面获得本地嵌入权限。若后续采用，增加显式本地嵌入配置并验证来源，保留其他安全头。

嵌入通过时可承载完整高级管理，也可作为补齐功能期间的入口。它本身不提供网关通用额度、当前模型识别或统一统计；这些仍需公开的数据/操作契约。

## 8. 当前需要补齐的公开能力

| 能力 | 当前情况 | 最小方向 |
| --- | --- | --- |
| 多连接供应商写入 | 单个 service 对应首个供应商 | 引入明确连接/供应商身份，继续走既有供应商写入流程 |
| Manager 数据适配 | 现有后台只封装部分接口 | 在同一用户拓展后台增加限名、参数校验的业务方法 |
| 普通供应商元数据 | WorkBuddy 专用连接当前只保留模型 ID，已有通用能力同步界面 | 复用现有模型、上下文与思考等级同步，维持截图中的卡片结构 |
| 网关通用额度 | 拓展供应商声明没有积分摘要回调 | 核对现有通用额度入口和契约；不足时补面向所有供应商的受限数据契约，不增加 WorkBuddy 专属组件 |
| Codex 模型使用 | 已有模型选择器和网关连接 | 沿用现有使用方式；管理能力只在 Codex++ 展示 |
| Key/池/模型统计 | 现有 by-model 无 Key/分组过滤 | 优先展示现有真实粒度；要精确交叉统计时补充后端查询及索引评估 |
| 连接/操作进度 | 部分方法同步等待，拓展调用有超时 | 长任务返回 operationId，查询/事件推送与重连恢复 |

后续拓展修改必须通过 `codexpp_extension_*` 工具进行，不直接写已安装目录，也不做成仓库内置拓展。本轮不修改宿主源码。通用额度能力属于平台契约建设，需要单独明确实现范围，不能用拓展覆盖整个供应商页或私自调用未开放命令替代。

通用额度数据建议只传非敏感 JSON：连接身份、额度单位、余额/已用/限制、Key 或账号池作用域、来源、观测时间和错误分类。账号数量、积分批次与管理动作保留在管理拓展中。凭据留在后端；管理页提供命名动作而非任意 URL/命令执行。

## 9. 模型使用的验收重点

协议先沿用当前已配置路径；对 Responses 与 Chat 两种接入分别检查实际工具和流式契约，再决定是否有必要减少一次协议转换。不得只凭接口名字选默认协议。

### 9.1 模型档位与上下文设置

模型能力同步是接入的核心交付项，不能只同步模型名称。默认档位和上下文预算使用 Codex++ 普通供应商“更多设置”的既有入口；通过已有模型目录让 Codex 现有选择器使用支持的思考档位，不新增 Codex 界面或状态侧栏。WorkBuddy 管理页可展示源能力及同步状态，不再维护第二套同义设置。

本轮源码核实：

- Manager 的模型目录已有 `efforts`、`default_effort`、`context_length`、`max_output_tokens`、积分倍率及能力说明；`context_length` 的腾讯来源是 `maxInputTokens`，不能未经验证称为输入和输出合计的总窗口。
- Manager 的 `/v1/models` 按 Key 绑定的上游和允许模型过滤，并有将 `reasoning_supported_efforts` 补成 `supported_reasoning_levels` 的兼容逻辑。优先保留这条路径的身份与能力，不绕过它展示 Key 实际不可用的模型。
- Codex++ 已有按供应商/模型编辑上下文和思考等级、从上游预览差异并选择写入的能力。元数据会参与 Agent 模型目录生成，优先复用，不另造重复控制台。
- 当前 WorkBuddy 专用连接的 `local_provider_gateway.rs::models` 只返回模型 ID；不能据此认为创建供应商时已同步能力。已有通用元数据同步可能补足 `/v1/models` 提供的字段，但尚未在本轮验证该连接的实际结果。
- Manager 管理目录目前提供单个输入上限；本轮没有发现可直接证明真实服务端上下文多档选择的字段。Codex++ 通用解析器虽识别 `context_windows` 数组，也不能据此声称当前 WorkBuddy 已提供该数组或相应请求能力。

推荐模型行与详情采用以下口径：

| 设置 | Codex++ 中的交互 | 生效要求 |
| --- | --- | --- |
| 思考强度 | 按当前连接实际支持的档位显示，标出默认档；中文说明旁保留原始值 | 目录、默认值、请求参数一致；不把所有模型都显示成支持 `max/ultra` |
| 上游输入/总窗口上限 | 分别展示可获得的原始能力及来源；字段不明确时标明口径 | 不能把 `maxInputTokens` 与输出上限相加后宣称为已验证总窗口 |
| 本地上下文预算 | 自动或手动预算，展示当前值和上游限制；可提供不超过可用上限的本地预设 | 控制 Agent 的上下文使用与压缩时机；改数字不提高上游实际能力 |
| 真实长上下文档位 | 仅在证实存在对应模型 ID 或服务参数时开放 | 请求必须携带真实档位；如果只是本地预算，必须明确标成本地预算 |
| 最大输出 | 显示上游声明值；输出预算的编辑与下发另行核实 | 与思考强度、输入预算分开；不能将输出长度当作上下文窗口 |
| 积分倍率 | 保留上游模型倍率、来源和更新时间 | 上游未提供档位/长上下文的额外计费规则时显示未知，不推算固定成本 |

详情中同时展示“上游能力”“用户默认设置”和“同步/生效状态”。例如，模型可以显示 `支持 low / high / max；默认 high；上游输入上限 …；本地预算 …`；该例仅说明布局，不代表任何具体模型的实际能力。

实现约束：

1. 能力以稳定连接、realm、上游池、Key 可见模型及真实模型 ID 为作用域；别名保留映射，不把国内版的档位套给国际版。同名模型属于不同池时不得无条件共享能力缓存。
2. 先读取 Key 范围内的 `/v1/models`；需要管理目录补全时取交集并核对 realm、模型映射和上游池。当前管理目录按 realm 取数，不能自动用默认池的元数据覆盖其他池。
3. 规范化 `efforts`/`supported_reasoning_levels` 与默认值。Manager 的产品兜底表与实时返回应区分来源；未声明、明确不支持和查询失败分别表示，不能一律称为“不支持推理”。
4. Codex++ 当前识别固定集合的思考档位。遇到其他值保留原文与兼容提示；`off` 等值只有验证语义及请求映射后才能映射，不能静默删除、冒充 `none` 或添加到原生选择器。
5. 切换模型时校验原思考强度，必要时使用目标模型支持的默认档并说明变化，不能继承目标模型不支持的档位。已发出的请求不因管理设置变更而重写。
6. 思考强度必须检查完整传递链：现有选择器 → Codex++ 请求及协议转换 → Manager → 上游。Manager 的 Responses 适配已有 `reasoning.effort` → `reasoning_effort` 转换，但仍需验证自动兼容逻辑不会把 WorkBuddy 的原始档位改成其他含义。
7. 保存默认设置与当前会话实际选择分开。继续复用同步差异预览和手动值保护；同步后分别报告供应商保存、Agent 配置刷新与可确认的会话状态，不能只显示一个含糊的“已生效”。
8. 本地预算按实际 Agent/网关计数及输出、工具预留规则校验；不能提供高于已知能力的普通预设。未知上限不自动填写大窗口，也不以“能保存配置”作为长上下文可用的证明。

### 9.2 端到端验收

必须覆盖：

- 原生模型列表出现、模型身份/能力一致、选中后请求确实到目标 WorkBuddy 池。
- 普通流式回复与连续多轮；工具发现、调用、返回以及并行工具结果。
- Code Mode、自定义/命名空间工具、长工具输出、中文路径和错误结果。
- 推理模型工具后续轮次；不支持的思考档位不能继承。
- 思考档位与默认值逐模型核对；国内/国际、同名不同池、产品兜底与未知档位；确认选中的实际值经过协议转换后仍正确发送，工具后续轮次不丢失。
- 上下文能力同步、本地预算保存与恢复、切换模型后的窗口更新；真实长上下文档位只在对应请求验证后标为可用。超限错误与压缩失败不能伪装成档位选择成功。
- 中途断流、合法失败终态、取消和超时；不把失败标成功。
- 长上下文与压缩：Manager 未见 `/responses/compact` 路由，需检查当前 Codex 实际请求路径及本地压缩行为，不能推定已支持。
- 图像/其他多模态只对目录与实际请求验证过的能力开放。
- 管理页关闭、拓展重载、Manager 重启后的连接恢复及已完成操作回读。

一次“Reply OK”只能证明基础链路，不能作为完整开发任务通过的证据。

## 11. 刷新、性能与数据可靠性

- 模型请求路径不等待账号列表、积分或统计查询。
- 页面打开时优先显示上次成功快照，随后异步更新；失败保留旧数值并标记时间。
- 账号运行状态可按可见页面短周期刷新；实时积分沿用上游缓存/限流，不逐请求查询。具体周期经本机测量后配置。
- 同一连接的多处界面共享后台缓存和在途请求；关闭页面取消页面级轮询。
- 当前账户余额要显示覆盖率；累计积分消耗与剩余余额独立保存，不能用余额差当成模型真实消耗。
- Key 与池归属变更后刷新绑定；旧历史保留原始维度，不能用今天的 Key 归属伪造历史分组。
- Manager 日志中的上游账号字段可能延迟回填；显示“待回填/未知”，不立即判定账号丢失。
